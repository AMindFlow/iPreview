# 规格、实现与验收

实质改动先确定规格和验收条件。规格按维度维护，一个维度回答一类长期问题，例如专辑如何分组、预览如何交互、原文件如何保护。同一功能可以同时受多个维度约束，每份规格只规定自己负责的结果。

1. **记录需求。** 需求提出时即登记 GitHub Issue 及[完整需求入口](../project/requirements.md)，待设计、待决定和未排期的需求一并记录。每条规格用稳定编号，链接到对应 Issue。讨论中改过口径时，链接到用户确认最终口径的评论。进度和优先级在 Projects 维护。
2. **确认规格。** 在 `spike/` 写拟改条目和可观察的验收条件。用户明确要求实施、且规格符合已确认的范围和口径时，可以直接推进。涉及用户可见行为、权限、数据、兼容性等实质取舍时，先澄清再实施。
3. **实现并验收。** 多种设计都能满足规格时，代理可以自行决定影响有限的细节，在规格里记下选择、依据和理由。代理负责执行客观检查，在 PR 按需求编号记录覆盖范围及结果。需要用户判断的验收条件由用户确认。
4. **更新生效规格。** 将确认后的条目和实现放进同一个 PR。通过验收并合入后，`official/` 中的条目生效。撤销或替换时，在同一 PR 更新 `superseded/`。一次性工作如果没有形成持续约束，缘由由 PR 和提交记录保存。

文件结构见[规格目录规则](../specs/AGENTS.md)。
