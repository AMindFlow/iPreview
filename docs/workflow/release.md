# 版本发布与双端交付

1. **记录版本范围。** 在版本登记册列出用户确认的功能、规格、Issue 与工作包 PR。持续跟踪未完成和待验证项目。按[开发流程](git.md)审阅当前提交，通过 CI 后处理阻塞审阅并走合并队列。版本号和安装器标识由独立发布改动或现有安装规格维护。
2. **构建最终主线。** 用同一个最终 `main` 提交构建 macOS ARM64 DMG 和应用 ZIP、Windows 11 x64 标准 EXE 和自包含 ZIP。核对包内资源、标识、版本、SHA-256、覆盖升级和卸载，记录构建任务链接。[标准安装包规格](../specs/official/platforms.md#plat-005-首版标准安装包)
3. **发布后准备安装。** 将包与校验文件发布到 GitHub Release。盘点两端旧应用、过时安装包和测试构建。按授权范围把过时物料移到回收站或其他可恢复位置，保留当前发行包、复用样例和继续开发所需分支及证据。需要正式空库时，先退出 iPreview 所有实例，按用户授权归档旧应用资料库整目录，再安装新版本。升级、卸载、数据恢复和真实源文件按各自规格处理。
4. **从发布物安装并复验。** 双端从 GitHub 下载正式 DMG／EXE，校验 SHA-256 后安装，从「应用程序」和开始菜单等正常入口启动。按版本范围用隔离 QA 库验证功能，并用可丢弃的旧版 QA 库验证升级和引用恢复。核对正常启动后的资料库与约定一致。正式空库交付场景在正常入口打开后留存首页，合成样例留在隔离库。[双端验收步骤](../project/acceptance.md)
5. **归档证据。** 在当前 GitHub Release 登记最终提交、构建任务、包名与 SHA-256、两端系统与安装入口、实际验证结果、未覆盖项、首页截图和清理清单。合成样例与证据按版本保存。版本登记册可链接 Release，提交号和产物清单由 Release 记录承担。
